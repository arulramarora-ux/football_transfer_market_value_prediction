# Football Player Market Value Predictor
## Build-Ready Product & Interface Specification

**Status:** Core interface-design decisions confirmed. The project is ready to begin implementation, with unresolved technical questions tracked below.

## 1. Product Goal

Build a full-stack web application that allows users to discover existing football players, view model-estimated market values, inspect available player statistics and model-supported explanations, and compare exactly two players.

The prediction target is a player's market value as of July 2026.

Keep these concepts distinct:
- **Model estimate:** The prediction generated by the project's ML model.
- **Recorded market valuation:** A value recorded in the source dataset.
- **Actual transfer fee:** The fee associated with a real transfer, when available.

Never present these values as interchangeable.

### MVP features
- Landing page and player discovery.
- Live player-search autocomplete and dedicated results page.
- Player profiles and historical recorded-value charts.
- Two-player comparison.
- Lightweight authentication and saved players/comparisons.
- Admin workflows for account, dataset, and model management.
- Loading, empty, error, and missing-data states.

### Out of scope
- Predicting hypothetical players absent from the supported dataset.
- Comparing more than two players at once.
- Fabricating historical values, statistics, or model explanations.
- Showing filters unsupported by the dataset.

## 2. Technical Architecture

- **Frontend:** React
- **Application backend/API:** Node.js
- **Inference service:** Python FastAPI
- **Offline model training:** scikit-learn
- **Database:** Neon PostgreSQL
- **Caching:** Redis-compatible cache

Keep responsibilities separate. The Node.js backend handles application workflows and data access; the Python service handles model inference.

Never expose database credentials, private API keys, or other secrets in the frontend. Validate inputs and handle service failures explicitly.

## 3. Visual Design System

### Visual direction
Football editorial: a premium scouting and analytics platform with football-focused typography, player imagery, club identity, and refined data visualizations.

### Color palette

| Token | Hex | Purpose |
|---|---|---|
| Page background | `#0B1220` | Main canvas |
| Card/surface | `#151F30` | Cards, panels, menus |
| Accent green | `#22C55E` | Primary actions and highlights |
| Primary text | `#F4F6FA` | Main content |
| Secondary text | `#94A3B8` | Supporting labels |

Use subtle borders, rounded corners, and restrained shadows. Reserve green for meaningful actions, focus states, selections, and important data highlights.

### Typography and density
- Editorial-style headings paired with a clean modern sans-serif body font.
- Readable numeric values, tables, and chart labels.
- Compact analytics layouts that show useful information without excessive whitespace.

### Buttons and controls
- Solid green primary buttons.
- Dark secondary buttons with clear borders.
- Readable, comfortably sized inputs.
- Clear hover, focus, disabled, loading, and error states.

### Motion and accessibility
- Use restrained animations and transitions.
- Respect reduced-motion preferences.
- Support keyboard navigation throughout the application.
- Maintain strong contrast and visible focus states.
- Label charts and controls appropriately.
- Never communicate important status through color alone.

### Responsive behavior
- Desktop-first but mobile-compatible.
- Public pages use a top navigation bar.
- Desktop analytics pages use a sidebar.
- Mobile layouts use compact navigation rather than squeezing the full sidebar.
- Simplify dense mobile layouts and permit horizontal scrolling for wide tables when needed.

## 4. Routes and Page Requirements

### `/` — Landing Page

Include:
1. Top navbar with product identity, player search, discovery, methodology, and account entry points.
2. Hero with a large headline on the left, permitted football imagery on the right, and a prominent search bar.
3. Featured or highest-valued players drawn from the actual dataset.
4. Selected dataset insights, only where supported by the data.
5. A "How it works" section covering the model, data, and limitations.
6. A call to action to explore players.
7. Footer with methodology and data notes.

### `/players` — Search and Results

- Search input with live autocomplete.
- Player results displayed in compact premium cards.
- Filters for position, age, league, and club, only when supported by the dataset.
- Sorting by name, age, and market value when the required field is available.
- Result count, clear-filters action, loading skeletons, and no-results state.

Autocomplete suggestions should show, where available:
- Player portrait or fallback.
- Name.
- Club.
- Position.
- Recorded market value.

Support keyboard navigation, selection, and dismissal. Debounce search requests to avoid unnecessary API calls.

### `/players/:id` — Player Profile

The top section should contain:
- Player portrait or fallback.
- Name, club, and position.
- Key available attributes.
- Prominent model-estimated market value.

Below it, show:
- Recorded market value separately, if available.
- Historical chart using actual recorded observations only.
- Key statistics present in the source data.
- A short plain-English model explanation.
- An expandable detailed explanation of supported positive and negative influences.
- Save/unsave player action.
- Add-to-comparison action.

Missing historical data or a failed prediction must not break the rest of the profile.

### `/compare` — Two-Player Comparison

Include:
- Selection of exactly two existing players.
- Side-by-side summary cards.
- Comparison table for fields available for both players.
- Clear labels for missing values.
- Historical recorded-value charts where observations exist.
- Model estimates and supported explanations for each player.
- Save-comparison action for signed-in users.

Never silently compare values with different definitions or invent missing values.

### `/sign-in` and `/sign-up`

- Clean, accessible forms.
- Clear field validation and error messages.
- Safe authentication behavior.
- Clear route back to public pages.

Use the authentication provider or session strategy selected for the project. Do not reveal sensitive account-existence details unnecessarily.

### `/saved` — Saved Items

Provide a lightweight saved-items page with:
- Saved players.
- Saved comparisons.
- Remove actions.
- Navigation to the relevant profile or comparison.
- Helpful empty states explaining how to save items.

A full personalized dashboard is not required.

### Account Menu

Include:
- Saved items.
- Sign-out.
- Other account actions only if implemented.

Saved data must always be scoped to the authenticated user.

### Admin Area

Restrict all admin pages and actions using server-verified roles and permissions.

Provide separate workflows for:
- Account administration.
- Dataset management.
- Model management.

Show dataset/model status, validation results, and actionable errors. Require confirmation for destructive actions. Keep admin navigation separate from ordinary user navigation.

The exact admin screens and permissions remain an implementation detail to finalize.

## 5. Player Images and Assets

Use real player portraits only when the source and usage rights permit their use.

Fallback order:
1. Permitted player portrait.
2. Relevant club badge.
3. Player initials.
4. Neutral silhouette.

Do not scrape or redistribute unlicensed images by default. Use consistent image dimensions and meaningful alt text.

## 6. Charts and Analytics

Use premium dark analytics styling:
- Green emphasis.
- Restrained gradient fills.
- Subtle gridlines.
- Clear axes and units.
- Refined tooltips.
- Consistent typography.

Rules:
- Historical charts may contain only actual recorded observations.
- Do not interpolate or fabricate missing values.
- Label dates and units.
- Provide an accessible textual or tabular summary.
- Handle zero, one, and multiple observations sensibly.
- If history is unavailable, explain that instead of displaying a decorative empty chart.
- Visually distinguish recorded valuations from model estimates.

## 7. Model Explanations and Trust

Use a two-level explanation:
1. Short plain-English summary.
2. Expandable detailed breakdown of supported positive and negative influences.

Detailed factors must come from a valid explanation method or actual model outputs.

If the model cannot support reliable feature attribution, omit unsupported claims and explain the limitation. Do not fabricate confidence or uncertainty estimates. Show uncertainty only if the pipeline provides a defensible estimate.

## 8. Loading, Empty, and Error States

Every data-driven page must handle:
- Loading skeletons.
- Empty search results.
- Missing optional fields.
- Missing historical observations.
- Player not found.
- Prediction unavailable or failed.
- Backend/network errors with retry where appropriate.
- Unauthorized admin access.
- Authentication and validation errors.
- Save/remove success and failure.

Do not replace failed production requests with fake data. If mock data is used during development, label it clearly and prevent it from leaking into production.

## 9. Interaction Rules

- Primary actions use green; secondary actions use dark surfaces and clear borders.
- Player cards lift subtly on hover and receive a restrained green border highlight.
- Keyboard focus must remain visible.
- Search autocomplete supports keyboard movement, selection, and dismissal.
- Filters reflect only available dataset fields.
- Saving requires authentication when account-based persistence is used.
- Comparison enforces the two-player limit.
- A failure in an optional chart must not block the whole page.

## 10. Suggested API Boundaries

Adapt endpoint names and payloads to the existing repository. These are proposed contracts, not claims that the routes already exist.

- `GET /api/players` — paginated list, query, filters, and sorting.
- `GET /api/players/:id` — player details and recorded attributes.
- `GET /api/players/:id/value-history` — dated recorded observations.
- `POST /api/predictions` — estimate for an existing supported player.
- `GET /api/me/saved-players` — retrieve authenticated user's saved players.
- `POST /api/me/saved-players` — save a player.
- `DELETE /api/me/saved-players/:id` — remove a saved player.
- Equivalent authenticated routes for saved comparisons.
- Admin-only routes for account, dataset, and model management.

Validate IDs and query parameters, paginate large lists, use structured errors, and avoid N+1 queries. Enforce authorization on the server, never through frontend-only checks.

## 12. Definition of Done

- Landing, search/results, profile, and comparison pages follow the design system.
- The interface works with keyboard and mouse.
- Desktop and mobile layouts have no overlapping primary controls.
- Search, filters, and sorting use supported fields only.
- Comparison never allows more than two players.
- Historical charts show only recorded observations.
- Model estimates, recorded valuations, and transfer fees are clearly distinguished.
- Explanations are backed by model outputs.
- Loading, empty, error, and missing-data states are implemented.
- Authentication and saved items are scoped to the correct user.
- Admin permissions are enforced server-side.
- No secrets are exposed to the frontend.
- Key flows and failure paths have tests.
